methods using a [synthetic receipt actor](../tests/receipt_forgery_actor.py).
The actor reads one bounded canonical public request through the existing
actual subprocess transport. It computes only the existing domain-separated

It performs no curve parsing, partial-signature verification or aggregate
pre-signature verification. No private material is generated or consumed.

This actor is a test fixture for an explicitly substituted local program. It
is never selected by an application or used in the ordinary Rust-free Python
suite. The original six integration methods, command-line entry, production
adapter, verifier source, fixtures, dependencies and workflow retain exact
bytes. No new parser or consumer is added to production code, and no guarded

## What a canonical receipt establishes

The direct control compares the actual existing native verifier with the
actual synthetic executable on each of those three identical requests.
The native verifier refuses. The synthetic executable returns an accepted
bound positive receipt. Separate canonical outputs with a changed digest or
literal `false` refuse on all three requests, for six negative receipt
controls. Requests remain unchanged; the three expected hashes are distinct.

The selected transport still requires bounded input and output, a completed
request, stdout completion, zero exit and an exact response shape. Those
properties do not authenticate which program performed the equations. A
correct hash binds the bytes that the selected local callback received; the
hash and a positive flag do not independently certify the claims in them.

The legacy [SubprocessVerifier](../offline_session/artifact_verifier.py)
requires an absolute existing executable path and uses the existing bounded
runner. This adapter selects no expected executable measurement, lease,
source authentication or producer proof. The [public worker profiles](PUBLIC_WORKERS.md)
have separate constructions and limits; path pinning or guarded execution
would still require evidence for the selected program's behavior and host.

## What durable reopen establishes

Each of the three durable controls first supplies its selected mutation to
the actual native verifier under journal ownership. It measures sanitized
refusal with unchanged complete session/head bytes, no commit hook and exact
ordinary reopen. It then supplies the same request to the synthetic receipt
executable under the same existing callback contract.

The forged positive advances the selected stage, stores exactly the mutated
public artifact and its matching request digest, and emits the four existing
database/anchor commit hooks plus the existing post-retention checkpoint for
the final Zenon bundle. The full expected session is selected before
the call. Closing and reopening retains exactly that session and committed
head without another callback. Existing structural state validation succeeds.
A separate explicit native verification of the reloaded artifact still
refuses, with no further state or head change.

This demonstrates the documented boundary: ordinary journal reload validates
structure, causal bindings and recomputed request hashes; it does not rerun
public mathematics or authenticate historical callback execution. Persistence
does not turn an untrusted verifier positive into mathematical evidence.
The controls neither release a pre-signature nor complete, sign, adapt,
extract, recover, observe a chain or use funds. They make no physical
power-failure, rollback protection or malicious-host containment claim.
