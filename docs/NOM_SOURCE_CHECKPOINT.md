# Historical NoM source and custody signatures

This additive profile binds three public signatures to an independently selected
complete NoM recovery context. It does not implement a trusted source service,
current chain observation, a nonrollback checkpoint store, or recovery admission.
Application and core remain **NO-GO**, every comparison remains **HOLD**, and
recovery action remains **NONE**.

## Independent selections and roles

Before interpreting peer signatures, the caller selects the entire network
profile, the root public key, two distinct delegated public keys, declaration
epoch, retained capsule, read query and exact raw source claim. The existing
[capsule/read binding](NOM_CAPSULE_QUERY.md) requires both actually retained
original envelopes and complete matching terms. A recovered signature without
its long original envelope cannot fill that requirement.

The new role declaration is separate from the old enrollment-governor profile:

| Signature | Selected signer | Complete signed message |
| --- | --- | --- |
| Root | Independently selected root key | Network profile, epoch, source-response key and consumer-checkpoint key |
| Source | Declared source-response key | Declaration, complete capsule/read binding, query, charged-work scope, exact raw claim and its coverage label |
| Custody checkpoint | Declared consumer-checkpoint key | Declaration, capsule and journal pins, all charged work, consumer incarnation and separately selected observer-retention pins |

The three keys must have distinct encodings. This establishes no distinct people,
organizations, custody domains or independently provisioned authority. A root
chosen from an incoming packet can produce valid mathematics under its own key.
Trusted root selection remains an external, unfilled requirement.

The selected network's root commitment hashes the raw root public key under
`ptlc-nom-selected-root-key-v1`. It is separate from the declaration digest,
avoiding a declaration that contains its own digest. The epoch is a selected
positive integer and is neither a journal sequence nor a trusted current revision.
Root transitions require independent reprovisioning; a signed old declaration
cannot authorize its own replacement or retirement.

## Message and wire construction

The selected construction uses the public signature/key widths and verification
algorithm in the pinned [BIP340 specification](https://github.com/bitcoin/bips/blob/2885f13d3f37890e328683166dbcbc60b488d13a/bip-0340.mediawiki).
Each message is `SHA256(domain || NUL || canonical_ASCII_JSON(payload))`:

| Payload | Domain |
| --- | --- |
| Declaration | `ptlc-nom-source-checkpoint-declaration-message-v1` |
| Source statement | `ptlc-nom-historical-source-message-v1` |
| Custody checkpoint | `ptlc-nom-historical-custody-message-v1` |
| Entire public verifier request, including all three signatures | `ptlc-nom-source-checkpoint-request-v1` |

These application domains and canonical framing are project choices, not BIP340
protocol requirements. Nothing is copied from the specification's text, code or
test vectors. The synthetic vectors are generated by this project's test-only
Rust generator using deliberately disclosed scalar tags. No application signer
or private key input is added. Existing public fixture encodings are reused;
existing enrollment roles, permissions, domains and signatures are not reused.

Objects require exact fields, lowercase hex, exact bounded positive integers,
ASCII canonical encoding and at most 12 JSON nesting levels. Requests are limited
to 8 KiB. The Python peer envelope accepts no trailing LF; the native stdin wire
allows one. Native results bind the entire request, including signature encodings.
An alternative valid signature therefore requires its own result digest.

Python performs selected-byte comparison, not curve verification. The separate
Rust worker checks the three public signatures with locked Bitcoin/libsecp256k1
dependencies. Go independently checks the same public fixtures with the existing
locked btcec dependency. Their parsing, role, domain and alias controls are separate.
No dependency version changes or consensus changes are introduced.

## Retention and replay boundary

The custody statement commits to the exact capsule and journal and the complete
list of previously charged ordinals. Every outcome stays `UNKNOWN` and possible
disclosure stays true. It does not claim that the signing party actually holds
those files or atomically persisted that statement. A hash is not a custody proof.
Observer-retention selection, head and sequence remain separate caller assertions;
they are never relabelled as the recovery journal or derived from its sequence.

A new source challenge changes the source statement, but cannot mint new work or
change the custody statement. Role rotation and a new declaration epoch change
the applicable declaration and checkpoint while preserving existing charged work.
An added unknown charge changes the checkpoint; an old signed tuple cannot match
that newer independently retained context. Rewrapping an old unsigned outer source
claim also cannot reuse the old source and checkpoint signatures for a new charge.

However, a coherent copy of the old root declaration, capsule, journal, query,
claim and signatures still verifies. The signed checkpoint has no external
nonrollback knowledge and cannot detect a restore of all selected state together.
Even an unavailable source claim can be correctly signed. Neither result proves
source truth, funding, finality, currentness or permission to act.

The Python verifier callback and selected executable/runtime remain trust
premises. A forged callback can report positive flags for zero signatures;
the actual native program refuses those signatures. Executable measurement and
remeasurement are not an atomic launch guarantee, loader attestation or sandbox.
The offline stream-capture harness has explicit trusted-process and memory limits.

## Next acceptance requirements

Operational source authentication requires independently provisioned roots and
network roles, authenticated evidence openings, selected canonicality/finality
and freshness policy, and independently assessed source behavior. Consumer
retention requires a checkpoint outside coherently copied state, explicit cold
start and recovery rules, and a separately qualified nonrollback storage design.
Only then can a distinct atomic work-entry mechanism be evaluated. Signing a
checkpoint or passing these tests satisfies none of those requirements.

Keep those application and observation mechanisms outside the narrow core node
contribution. Deployment, activation, wallet access, application signing,
transaction construction, broadcast and real funds remain outside this workspace.
See the [qualification boundary](NOM_SOURCE_CHECKPOINT_VALIDATION.md).
